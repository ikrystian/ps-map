1.1. PRZEGLĄD FUNKCJONALNOŚCI
--------------------------------------------------------------------------------

Moduł transakcji to centrum zarządzania wszystkimi płatnościami w systemie
Prosta Sprawa. Administrator ma pełen wgląd i kontrolę nad zamówieniami
składanymi przez kancelarie prawne, zarówno dotyczącymi zakupu punktów
promocyjnych, jak i subskrypcji pakietów abonamentowych.

GŁÓWNE CELE MODUŁU:
- Pełna widoczność wszystkich transakcji w systemie
- Możliwość manualnej aktualizacji statusów płatności
- Monitoring przychodów i działań finansowych kancelarii
- Identyfikacja i rozwiązywanie problemów płatności
- Generowanie statystyk finansowych

--------------------------------------------------------------------------------

Strona: /admin/transakcje
Dostęp: Tylko użytkownicy z rolą ADMIN
Plik źródłowy: prosta-sprawa/app/admin/transakcje/page.tsx

B) KARTY STATYSTYCZNE (4 karty w rzędzie)

C) PANEL FILTRÓW (4 pola w rzędzie)

   Pole 1: WYSZUKIWANIE TEKSTOWE

   Pole 3: METODA PŁATNOŚCI
   - Typ: Select dropdown
   - Opcje:

   - Typ: Select dropdown
   - Opcje:

   - NASTĘPNA (disabled na ostatniej stronie)

   Limit: 20 transakcji na stronę


1.3. TYPY TRANSAKCJI
--------------------------------------------------------------------------------

System obsługuje dwa główne typy zamówień:

A) PUNKTY (OrderType.POINTS)

   Zastosowanie:
   - Zakup pakietów punktów promocyjnych przez kancelarię
   - Punkty służą do aktywacji promocji profilu

   Pola specyficzne:
   - pakietPunktow: String - nazwa pakietu (np. "100_pkt", "250_pkt", "500_pkt")
   - liczbaPunktow: Int - liczba punktów w pakiecie

   Przykładowe pakiety:
   - 100 punktów
   - 250 punktów
   - 500 punktów
   - 1000 punktów

   Akcje po płatności:
   - Dodanie punktów do salda kancelarii (punktySaldo)
   - Wygenerowanie faktury VAT

B) SUBSKRYPCJA (OrderType.SUBSCRIPTION)

   Zastosowanie:
   - Zakup lub odnowienie pakietu abonamentowego
   - Dostęp do funkcji premium platformy

   Pola specyficzne:
   - subscriptionPlanId: String - ID wybranego planu
   - subscriptionPlan: Relacja - plan (Podstawowy, Standard, Premium, Biznes)
   - subscriptionPeriod: Int - okres w miesiącach (1, 6, 12)
   - packageStartDate: DateTime - data rozpoczęcia abonamentu
   - packageEndDate: DateTime - data zakończenia abonamentu

   Akcje po płatności:
   - Aktualizacja subscriptionPlanId w profilu kancelarii
   - Ustawienie dat rozpoczęcia/zakończenia pakietu
   - Wygenerowanie faktury VAT


1.4. FILTRY I WYSZUKIWANIE
--------------------------------------------------------------------------------

System filtrowania działa w czasie rzeczywistym i obsługuje:

A) WYSZUKIWANIE TEKSTOWE

   API Endpoint: GET /api/admin/transakcje?search={query}

   Przeszukiwane pola:
   - orderNumber (numer zamówienia)
   - transactionId (ID transakcji z bramki płatności)
   - externalOrderId (zewnętrzne ID z PayU/Przelewy24)
   - lawFirm.nazwa (nazwa osoby/prawnika)
   - lawFirm.nazwaFirmy (nazwa firmy)

   Tryb: Case-insensitive (bez rozróżniania wielkości liter)
   Operator: contains (zawiera frazę)

B) FILTROWANIE PO STATUSIE PŁATNOŚCI

   API Endpoint: GET /api/admin/transakcje?statusPlatnosci={status}

   Dostępne statusy:
   - OCZEKUJE: Płatność oczekująca
   - ZAPLACONE: Płatność zrealizowana
   - ANULOWANE: Transakcja anulowana
   - ZWROT: Zwrot środków

C) FILTROWANIE PO METODZIE PŁATNOŚCI

   API Endpoint: GET /api/admin/transakcje?metodaPlatnosci={method}

   Dostępne metody:
   - PAYU: Bramka PayU
   - PRZELEWY24: Bramka Przelewy24
   - PRZELEW: Przelew bankowy tradycyjny
   - PAYPAL: PayPal
   - BACS: BACS (UK)

D) FILTROWANIE PO TYPIE ZAMÓWIENIA

   API Endpoint: GET /api/admin/transakcje?orderType={type}

   Dostępne typy:
   - POINTS: Zamówienia punktów
   - SUBSCRIPTION: Zamówienia subskrypcji

E) KOMBINOWANIE FILTRÓW

   Wszystkie filtry mogą być używane jednocześnie:

   Przykład:
   GET /api/admin/transakcje?search=Kowalski&statusPlatnosci=ZAPLACONE&metodaPlatnosci=PRZELEWY24&orderType=POINTS&page=1&limit=20


1.5. STATYSTYKI I PODSUMOWANIA
--------------------------------------------------------------------------------

Dashboard wyświetla kluczowe metryki finansowe:

A) CAŁKOWITA LICZBA TRANSAKCJI
   - Źródło: pagination.total

B) OCZEKUJĄCE PŁATNOŚCI

C) ZAPŁACONE TRANSAKCJE

D) SUMA PRZYCHODÓW
   - Suma wartości wszystkich zapłaconych transakcji
   - Format: Polski format waluty z symbolem "zł"
   - Przykład: "12 450,50 zł"
   - Kalkulacja:
     orders
       .filter(o => o.statusPlatnosci === "ZAPLACONE")
       .reduce((sum, o) => sum + o.kwota, 0)


1.6. OPERACJE NA TRANSAKCJACH
--------------------------------------------------------------------------------

Administrator może wykonywać następujące operacje:

A) EDYCJA TRANSAKCJI

   Przycisk: Ikona Edit w kolumnie Akcje
   Dialog: "Edytuj transakcję"

   Edytowalne pola:

   1. STATUS PŁATNOŚCI (wymagane)
      - Select dropdown
      - Opcje: OCZEKUJE, ZAPLACONE, ANULOWANE, ZWROT
      - Wpływ: Zmiana statusu może wywołać akcje systemowe

   2. METODA PŁATNOŚCI (wymagane)
      - Select dropdown
      - Opcje: PAYU, PRZELEWY24, PRZELEW, PAYPAL, BACS

   3. KWOTA (wymagane)
      - Input numeryczny
      - Krok: 0.01
      - Jednostka: PLN
      - Walidacja: Musi być dodatnia liczba

   4. ID TRANSAKCJI (opcjonalne)
      - Input tekstowy
      - Przechowuje ID z bramki płatności
      - Używane do reconciliation płatności

   5. ZEWNĘTRZNE ID ZAMÓWIENIA (opcjonalne)
      - Input tekstowy
      - ID nadane przez PayU/Przelewy24
      - Pomocne przy debugowaniu integracji

   Akcje po zapisie:
   - Aktualizacja rekord Order w bazie danych
   - Jeśli zmieniono status na ZAPLACONE:
     * Ustawienie zaplaconoData na aktualną datę/czas
     * Dodanie punktów do salda (dla zamówień POINTS)
     * Generowanie faktury (jeśli nie istnieje)
   - Odświeżenie listy transakcji
   - Toast: "Transakcja została zaktualizowana"

   API Endpoint: PUT /api/admin/transakcje/[id]

B) USUWANIE TRANSAKCJI

   Przycisk: Ikona Trash2 w kolumnie Akcje
   Dialog potwierdzenia: AlertDialog

   Tytuł: "Czy na pewno chcesz usunąć tę transakcję?"
   Opis: "Ta operacja jest nieodwracalna. Transakcja zostanie trwale
          usunięta z systemu."

   Przyciski:
   - ANULUJ: Zamyka dialog bez akcji
   - USUŃ: Wykonuje usunięcie

   Skutki usunięcia:
   - Trwałe usunięcie rekordu Order z bazy
   - Kaskadowe usunięcie powiązanej faktury (jeśli istnieje)
   - NIE cofa dodanych punktów (należy ręcznie skorygować)
   - Toast: "Transakcja została usunięta"

   API Endpoint: DELETE /api/admin/transakcje/[id]

   UWAGA: Operacja nieodwracalna! Należy używać ostrożnie.


1.7. AUTOMATYCZNE DZIAŁANIA SYSTEMOWE
--------------------------------------------------------------------------------

Przy zmianie statusu transakcji na ZAPLACONE system wykonuje:

A) AKTUALIZACJA DATY PŁATNOŚCI
   - Pole: zaplaconoData
   - Wartość: Aktualna data i czas
   - Używane do raportowania i statystyk

B) DODANIE PUNKTÓW (tylko dla OrderType.POINTS)

   Warunek: order.orderType === "POINTS" && order.liczbaPunktow > 0

   Akcja:
   await prisma.lawFirm.update({
     where: { id: order.lawFirmId },
     data: {
       punktySaldo: {
         increment: order.liczbaPunktow
       }
     }
   })

   Rezultat: Saldo punktów kancelarii zwiększa się o zakupioną liczbę

C) GENEROWANIE FAKTURY VAT

   Warunek: Brak powiązanej faktury

   Proces:
   1. Wywołanie: generateInvoiceForOrder(order.id)
   2. Generowanie numeru faktury (format: FV/YYYY/MM/XXXXX)
   3. Kalkulacja kwot:
      - Kwota brutto = order.kwota
      - Stawka VAT = 23%
      - Kwota netto = brutto / 1.23
      - Kwota VAT = brutto - netto
   4. Zapisanie danych nabywcy z profilu kancelarii:
      - Nazwa firmy
      - NIP
      - Adres, kod pocztowy, miasto
   5. Utworzenie rekordu Invoice w bazie
   6. Status faktury: ISSUED (wystawiona)

   Szczegóły w pliku: lib/invoice-generator.ts

1.9. MODEL DANYCH
--------------------------------------------------------------------------------

MODEL: Order
Lokalizacja: prisma/schema.prisma (linie 946-990)

model Order {
  id                String   @id @default(uuid())
  orderNumber       String?  @unique
  lawFirmId         String
  lawFirm           LawFirm  @relation(fields: [lawFirmId], references: [id], onDelete: Cascade)

  // Typ zamówienia
  orderType         OrderType @default(POINTS)

  // Dla zamówień punktów
  pakietPunktow     String?
  liczbaPunktow     Int?

  // Dla zamówień subskrypcji
  subscriptionPlanId String?
  subscriptionPlan   SubscriptionPlan? @relation(fields: [subscriptionPlanId], references: [id])
  subscriptionPeriod Int?
  packageStartDate   DateTime?
  packageEndDate     DateTime?

  // Wspólne pola
  kwota             Float

  metodaPlatnosci   PaymentMethod
  statusPlatnosci   PaymentStatus @default(OCZEKUJE)

  // Dane rozliczeniowe
  daneFaktury       String?

  // Integracja z bramkami płatności
  externalOrderId   String?
  transactionId     String?
  statusUrl         String?
  redirectUrl       String?

  // Daty
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt
  zaplaconoData     DateTime?

  // Relacje
  invoice           Invoice?

  @@index([lawFirmId])
  @@index([statusPlatnosci])
  @@index([metodaPlatnosci])
  @@index([orderType])
  @@index([createdAt])
}

ENUMY:

enum OrderType {
  POINTS        // Zakup punktów
  SUBSCRIPTION  // Zakup subskrypcji
}

enum PaymentMethod {
  PAYU
  PRZELEWY24
  PRZELEW
  PAYPAL
  BACS
}

enum PaymentStatus {
  OCZEKUJE
  ZAPLACONE
  ANULOWANE
  ZWROT
}

2.1. PRZEGLĄD FUNKCJONALNOŚCI
--------------------------------------------------------------------------------

Moduł konfiguracji promocji pozwala administratorowi na definiowanie
i zarządzanie typami promocji dostępnych dla kancelarii prawnych.

Każdy typ promocji określa:
- Nazwę i opis promocji
- Koszt w punktach (dziennie lub tygodniowo)
- Cechy/benefity promocji
- Wygląd (ikona, kolor)
- Status aktywności
- Kolejność wyświetlania

GŁÓWNE CELE MODUŁU:
- Centralna konfiguracja dostępnych promocji
- Elastyczne zarządzanie cenami promocji
- Możliwość dodawania nowych typów promocji
- Kontrola nad aktywnością poszczególnych promocji
- Dostosowywanie opisów i cech promocji


2.2. INTERFEJS UŻYTKOWNIKA
--------------------------------------------------------------------------------

Strona: /admin/promocje
Dostęp: Tylko użytkownicy z rolą ADMIN
Plik źródłowy: prosta-sprawa/app/admin/promocje/page.tsx

SEKCJE INTERFEJSU:

A) NAGŁÓWEK STRONY

   Lewa strona:
   - Tytuł: "Zarządzanie promocjami"
   - Opis: "Konfiguruj typy promocji dostępne dla kancelarii"

   Prawa strona:
   - Przycisk: "Dodaj typ promocji"
   - Ikona: Plus
   - Akcja: Otwiera dialog tworzenia nowej konfiguracji

B) SIATKA KART PROMOCJI

   Layout: Grid 2 kolumny (md:grid-cols-2)

   Każda karta zawiera:

   NAGŁÓWEK KARTY:
   - Ikona: TrendingUp (primary color)
   - Tytuł: Label promocji (np. "Podbicie ogłoszenia")
   - Opis: Description promocji
   - Badge statusu: "Aktywna" (zielony) lub "Nieaktywna" (szary)

   ZAWARTOŚĆ KARTY:

   Sekcja 1: TYP
   - Label: "Typ:"
   - Wartość: Badge z typem promocji (np. "PODBICIE_OGLOSZENIA")

   Sekcja 2: KOSZT
   - Label: "Koszt:"
   - Wartość: Badges pokazujące koszt
     * Jeśli pointsPerDay: "{X} pkt/dzień"
     * Jeśli pointsPerWeek: "{X} pkt/tydzień"

   Sekcja 3: CECHY

2.3. TYPY PROMOCJI
--------------------------------------------------------------------------------

System definiuje 4 typy promocji (enum PromotionType):

A) PODBICIE_OGLOSZENIA

   Opis: Zwiększa widoczność profilu kancelarii w wynikach wyszukiwania

   Typowe parametry:
   - Koszt: 20 pkt/dzień
   - Cechy:
     * Wyższa pozycja w wynikach wyszukiwania
     * Podbicie co 24h
     * Większa widoczność profilu

   Zastosowanie:
   - Kancelaria chce być wyżej w listach
   - Krótkoterminowe kampanie promocyjne
   - Testowanie efektywności promocji

B) WYROZNIENIE

   Opis: Wizualne wyróżnienie profilu kancelarii

   Typowe parametry:
   - Koszt: 50 pkt/tydzień
   - Cechy:
     * Kolorowe tło karty profilu
     * Badge "Wyróżnione"
     * Zwiększona widoczność
     * Wyróżnienie przez 7 dni

   Zastosowanie:
   - Wyróżnienie się na tle konkurencji
   - Przyciągnięcie uwagi klientów
   - Średnioterminowa promocja

C) TOP_LISTA

   Opis: Umieszczenie w sekcji TOP kancelarii

   Typowe parametry:
   - Koszt: 100 pkt/tydzień
   - Cechy:
     * Wyświetlanie w sekcji TOP na stronie kategorii
     * Priorytet w wynikach wyszukiwania
     * Zwiększony ruch na profilu
     * Promocja przez 7 dni

   Zastosowanie:
   - Premium positioning
   - Maksymalna widoczność w kategorii
   - Długoterminowa strategia marketingowa

D) STRONA_GLOWNA

   Opis: Promocja na stronie głównej platformy

   Typowe parametry:
   - Koszt: 200 pkt/tydzień
   - Cechy:
     * Wyświetlanie na stronie głównej
     * Maksymalna widoczność w całym serwisie
     * Dotarcie do wszystkich odwiedzających
     * Premium placement przez 7 dni

   Zastosowanie:
   - Najwyższa forma promocji
   - Największy zasięg
   - Budowanie rozpoznawalności marki


2.4. PARAMETRY KONFIGURACJI
--------------------------------------------------------------------------------

Każda konfiguracja promocji zawiera następujące parametry:

A) PODSTAWOWE INFORMACJE

   1. TYPE (String, wymagane, unikalne)
      - Enum: PromotionType
      - Wartości: PODBICIE_OGLOSZENIA, WYROZNIENIE, TOP_LISTA, STRONA_GLOWNA
      - Unikalny klucz identyfikujący typ promocji
      - Nie może być zmieniany po utworzeniu

   2. LABEL (String, wymagane)
      - Nazwa wyświetlana użytkownikowi
      - Przykład: "Podbicie ogłoszenia"
      - Używane w interfejsie kancelarii

   3. DESCRIPTION (String, wymagane)
      - Opis promocji
      - Przykład: "Zwiększ widoczność swojego profilu w wynikach wyszukiwania"
      - Wyświetlany w panelu kancelarii przy wyborze promocji

B) CENY

   4. POINTS_PER_DAY (Int, opcjonalne)
      - Koszt promocji za jeden dzień
      - Null jeśli promocja nie jest rozliczana dziennie
      - Przykład: 20

   5. POINTS_PER_WEEK (Int, opcjonalne)
      - Koszt promocji za tydzień (7 dni)
      - Null jeśli promocja nie jest rozliczana tygodniowo
      - Przykład: 100

   UWAGA: Przynajmniej jedno z pól pointsPerDay lub pointsPerWeek
          musi być wypełnione!

C) CECHY/BENEFITY

   6. FEATURES (String - JSON array, wymagane)
      - Lista cech/benefitów promocji
      - Format: JSON.stringify(["Cecha 1", "Cecha 2", ...])
      - Przykład: ["Wyższa pozycja w wynikach", "Podbicie co 24h"]
      - Wyświetlane jako lista punktorów w interfejsie
      - Minimum 1 cecha wymagana

D) WYGLĄD

   7. ICON (String, opcjonalne)
      - Nazwa ikony z biblioteki lub URL do ikony
      - Przykład: "TrendingUp", "Star", "Zap"
      - Null jeśli nie ustawiono
      - Używane przy wyświetlaniu promocji

   8. COLOR (String - hex, opcjonalne)
      - Kolor tła ikony lub karty promocji
      - Format: Hex color (np. "#3b82f6")
      - Default: "#3b82f6" (niebieski)
      - Null jeśli nie ustawiono

E) STATUS I KOLEJNOŚĆ

   9. AKTYWNA (Boolean, wymagane)
      - Określa czy promocja jest dostępna dla kancelarii
      - true: Promocja widoczna i możliwa do aktywacji
      - false: Promocja ukryta, niedostępna
      - Default: true

   10. KOLEJNOSC (Int, wymagane)
       - Kolejność wyświetlania w liście promocji
       - Niższe wartości = wyżej na liście
       - Default: 0
       - Używane do sortowania: orderBy: { kolejnosc: 'asc' }

F) METADANE

   11. CREATED_AT (DateTime)
       - Data utworzenia konfiguracji
       - Automatycznie ustawiane

   12. UPDATED_AT (DateTime)
       - Data ostatniej aktualizacji
       - Automatycznie aktualizowane przy każdej zmianie


2.5. OPERACJE ADMINISTRACYJNE
--------------------------------------------------------------------------------

Administrator może wykonywać następujące operacje:

A) DODAWANIE NOWEJ KONFIGURACJI

   Przycisk: "Dodaj typ promocji"
   Dialog: "Dodaj konfigurację promocji"

   Proces:
   1. Kliknięcie przycisku otwiera dialog
   2. Administrator wypełnia formularz
   3. Walidacja po stronie klienta:
      - Wszystkie pola wymagane wypełnione
      - Przynajmniej jedno pole koszt wypełnione
      - Co najmniej jedna cecha dodana
   4. Wysłanie POST /api/admin/promotion-configs
   5. Walidacja po stronie serwera:
      - Sprawdzenie czy typ już nie istnieje (unique constraint)
      - Walidacja formatu danych
   6. Utworzenie rekordu w bazie
   7. Toast: "Konfiguracja promocji została utworzona"
   8. Odświeżenie listy konfiguracji

   Możliwe błędy:
   - "Type, label, and description are required"
   - "Either pointsPerDay or pointsPerWeek must be provided"
   - "Features must be an array"
   - "Promotion config with this type already exists"

B) EDYCJA KONFIGURACJI

   Przycisk: Ikona Edit na karcie promocji
   Dialog: "Edytuj konfigurację promocji"

   Proces:
   1. Kliknięcie Edit otwiera dialog z wypełnionymi danymi
   2. Pole TYPE jest zablokowane (disabled)
   3. Administrator modyfikuje inne pola
   4. Walidacja jak przy dodawaniu
   5. Wysłanie PUT /api/admin/promotion-configs/[id]
   6. Aktualizacja rekordu w bazie
   7. Toast: "Konfiguracja promocji została zaktualizowana"
   8. Odświeżenie listy

   Uwaga: Zmiana ceny lub statusu aktywności wpływa na:
   - Nowe aktywacje promocji przez kancelarie
   - Aktywne promocje NIE są automatycznie aktualizowane
   - Należy rozważyć komunikację z kancelariami o zmianach

C) USUWANIE KONFIGURACJI

   Przycisk: Ikona Trash2 na karcie promocji
   Potwierdzenie: Browser confirm dialog

   Tekst potwierdzenia:
   "Czy na pewno chcesz usunąć tę konfigurację promocji?"

   Proces:
   1. Kliknięcie Usuń pokazuje confirm dialog
   2. Użytkownik potwierdza lub anuluje
   3. Wysłanie DELETE /api/admin/promotion-configs/[id]
   4. Usunięcie rekordu z bazy
   5. Toast: "Konfiguracja promocji została usunięta"
   6. Odświeżenie listy

   UWAGA KRYTYCZNA:
   - Usunięcie konfiguracji NIE usuwa aktywnych promocji kancelarii
   - Aktywne promocje mogą dalej działać, ale nie będą miały
     pełnych metadanych
   - Zalecane: Najpierw dezaktywować (aktywna = false),
     poczekać aż wszystkie aktywne promocje wygasną,
     dopiero wtedy usunąć konfigurację

D) AKTYWACJA/DEZAKTYWACJA

   Mechanizm: Edycja + zmiana pola "Aktywna"

   Aktywna = true:
   - Promocja widoczna w panelu kancelarii
   - Możliwa do zakupu i aktywacji
   - Wyświetlana w ofercie promocji

   Aktywna = false:
   - Promocja ukryta w panelu kancelarii
   - Niemożliwa do zakupu
   - Aktywne promocje tego typu dalej działają
   - Przydatne przy wycofywaniu typu promocji

E) ZMIANA KOLEJNOŚCI

   Mechanizm: Edycja + zmiana pola "Kolejność"

   Zastosowanie:
   - Określa kolejność wyświetlania w liście promocji
   - Niższe wartości = wyżej na liście
   - Przykład:
     * Kolejność 0: PODBICIE_OGLOSZENIA (najpierw)
     * Kolejność 1: WYROZNIENIE
     * Kolejność 2: TOP_LISTA
     * Kolejność 3: STRONA_GLOWNA (ostatnie)

2.7. MODEL DANYCH
--------------------------------------------------------------------------------

MODEL: PromotionConfig
Lokalizacja: prisma/schema.prisma (linie 1057-1086)

model PromotionConfig {
  id                String   @id @default(uuid())

  // Typ promocji
  type              PromotionType @unique
  label             String
  description       String

  // Koszt
  pointsPerDay      Int?
  pointsPerWeek     Int?

  // Cechy/Features (JSON array stringów)
  features          String   // JSON: ["Feature 1", "Feature 2", ...]

  // Ikona i wygląd
  icon              String?
  color             String?

  // Status
  aktywna           Boolean  @default(true)
  kolejnosc         Int      @default(0)

  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  @@index([type])
  @@index([aktywna])
  @@index([kolejnosc])
}

ENUM: PromotionType
Lokalizacja: prisma/schema.prisma (linie 1046-1051)

enum PromotionType {
  PODBICIE_OGLOSZENIA
  WYROZNIENIE
  TOP_LISTA
  STRONA_GLOWNA
}

INDEKSY:
- type: Szybkie wyszukiwanie po typie (również unique constraint)
- aktywna: Filtrowanie aktywnych/nieaktywnych
- kolejnosc: Sortowanie przy wyświetlaniu

RELACJE:
- Model PromotionConfig NIE ma bezpośrednich relacji z innymi modelami
- Typ promocji jest używany w modelu Promotion (aktywne promocje kancelarii)
- Ale nie ma foreign key constraint - to luźne powiązanie

3.1. SYSTEM PUNKTÓW
--------------------------------------------------------------------------------

Punkty to wirtualna waluta w systemie Prosta Sprawa, używana przez kancelarie
do aktywacji promocji profilu.

PRZEPŁYW PUNKTÓW:

A) ZAKUP PUNKTÓW

   1. Kancelaria wybiera pakiet punktów w panelu (/panel-kancelarii/punkty)
   2. Tworzone jest zamówienie typu POINTS
   3. Przekierowanie do bramki płatności (PayU/Przelewy24)
   4. Po udanej płatności:
      - Status zamówienia zmienia się na ZAPLACONE
      - Punkty dodawane do lawFirm.punktySaldo
      - Generowana faktura VAT

   Implementacja dodawania punktów:
   await prisma.lawFirm.update({
     where: { id: lawFirmId },
     data: {
       punktySaldo: {
         increment: liczbaPunktow
       }
     }
   })

B) WYDAWANIE PUNKTÓW

   1. Kancelaria aktywuje promocję w panelu (/panel-kancelarii/promowanie)
   2. System sprawdza saldo punktów
   3. Jeśli saldo wystarczające:
      - Tworzona jest aktywna promocja (model Promotion)
      - Punkty odejmowane z punktySaldo
      - Rozpoczyna się okres promocji

   Implementacja (w transakcji):
   await prisma.$transaction([
     // Odejmij punkty
     prisma.lawFirm.update({
       where: { id: lawFirmId },
       data: {
         punktySaldo: {
           decrement: koszt
         }
       }
     }),
     // Utwórz promocję
     prisma.promotion.create({
       data: {
         lawFirmId,
         type,
         startDate,
         endDate,
         pointsCost: koszt
       }
     })
   ])

C) ZWROT PUNKTÓW

   Możliwe w przypadku:
   - Anulowania zamówienia (status ANULOWANE)
   - Zwrotu płatności (status ZWROT)
   - Przedwczesnego zakończenia promocji

   Administrator może ręcznie dodać punkty w panelu lub przez API


3.2. GENEROWANIE FAKTUR
--------------------------------------------------------------------------------

Faktury VAT są automatycznie generowane dla wszystkich zapłaconych zamówień.

PROCES GENEROWANIA:

A) WYZWALACZ

   Faktura generowana gdy:
   1. Zamówienie zmienia status na ZAPLACONE
   2. I NIE ma jeszcze powiązanej faktury

   Wywołanie: generateInvoiceForOrder(orderId)

B) NUMERACJA FAKTUR

   Format: FV/YYYY/MM/XXXXX

   Gdzie:
   - FV: Prefiks "Faktura VAT"
   - YYYY: Rok (4 cyfry)
   - MM: Miesiąc (2 cyfry z zerem wiodącym)
   - XXXXX: Numer sekwencyjny w miesiącu (5 cyfr z zerami wiodącymi)

   Przykłady:
   - FV/2025/01/00001
   - FV/2025/01/00123
   - FV/2025/12/09999

   Licznik resetuje się każdego miesiąca.

C) KALKULACJA KWOT

   Ceny w systemie są brutto (z VAT 23%):

   grossAmount = order.kwota                    // Kwota brutto
   vatRate = 23.0                               // Stawka VAT 23%
   netAmount = grossAmount / 1.23               // Kwota netto
   vatAmount = grossAmount - netAmount          // Kwota VAT

   Przykład dla 49,00 zł brutto:
   - Kwota brutto: 49,00 zł
   - Kwota netto: 39,84 zł
   - Kwota VAT: 9,16 zł
   - Stawka VAT: 23%

D) DANE NABYWCY

   Pobierane z profilu LawFirm w momencie wystawienia:
   - buyerName: nazwaFirmy lub nazwa
   - buyerNIP: nip (opcjonalnie)
   - buyerAddress: adres
   - buyerPostalCode: kodPocztowy
   - buyerCity: miasto
   - buyerCountry: "Polska" (domyślnie)

   Uwaga: Dane są kopiowane do faktury, więc późniejsze zmiany
   w profilu kancelarii NIE wpływają na wystawione faktury.

E) DATY

   - issueDate: Data wystawienia = data zmiany statusu na ZAPLACONE
   - saleDate: Data sprzedaży = data wystawienia
   - paymentDate: Data płatności = order.zaplaconoData
   - dueDate: Termin płatności = data płatności (już zapłacone)

F) STATUS FAKTURY

   - Domyślny: ISSUED (wystawiona)
   - Możliwe statusy:
     * DRAFT: Szkic
     * ISSUED: Wystawiona
     * SENT: Wysłana do klienta
     * PAID: Opłacona
     * CANCELLED: Anulowana

G) PLIK IMPLEMENTACJI

   Lokalizacja: lib/invoice-generator.ts

   Funkcje:
   - generateInvoiceForOrder(orderId): Generuje fakturę dla zamówienia
   - markOrderAsPaidAndGenerateInvoice(orderId, transactionId):
     Oznacza jako zapłacone i generuje fakturę


3.3. SYSTEM PŁATNOŚCI
--------------------------------------------------------------------------------

Platforma integruje się z zewnętrznymi bramkami płatności.

OBSŁUGIWANE BRAMKI:

A) PRZELEWY24
   - Główna bramka płatności w Polsce
   - Obsługa kart, szybkich przelewów, BLIK
   - Webhook dla potwierdzenia płatności

B) PAYU
   - Alternatywna bramka płatności
   - Obsługa kart i przelewów
   - Callback URL dla statusu

C) PRZELEW BANKOWY
   - Tradycyjny przelew
   - Wymaga manualnego potwierdzenia przez admina
   - Dane do przelewu wyświetlane po złożeniu zamówienia

D) PAYPAL
   - Płatności międzynarodowe
   - Obsługa kart i kont PayPal

E) BACS (UK)
   - System przelewów w UK
   - Dla klientów brytyjskich

PRZEPŁYW PŁATNOŚCI:

1. Utworzenie zamówienia (Order)
   - Status: OCZEKUJE
   - Wygenerowanie externalOrderId

2. Przekierowanie do bramki płatności
   - URL przekierowania zapisany w redirectUrl
   - Webhook URL dla powiadomień zapisany w statusUrl

3. Realizacja płatności przez użytkownika
   - W interfejsie bramki płatności

4. Callback/Webhook od bramki
   - Bramka wysyła potwierdzenie płatności
   - Endpoint: /api/payments/callback lub podobny
   - Aktualizacja statusu zamówienia

5. Potwierdzenie płatności
   - Status zmienia się na ZAPLACONE
   - Wykonywane są akcje post-płatności:
     * Dodanie punktów (dla POINTS)
     * Aktywacja subskrypcji (dla SUBSCRIPTION)
     * Generowanie faktury

6. Przekierowanie użytkownika
   - Success page: /panel-kancelarii/checkout/success
   - Wyświetlenie potwierdzenia i numeru zamówienia

MANUALNA AKTUALIZACJA:

Administrator może manualnie zmienić status płatności w /admin/transakcje:
- Przydatne dla przelewów tradycyjnych
- Rozwiązywanie problemów z callbackiem
- Korekty i zwroty

UWAGA: Manualna zmiana statusu na ZAPLACONE wywołuje te same akcje
co automatyczne potwierdzenie (punkty, faktura, etc.)
